# 会话工作区目录视图

## 问题

会话看板原先按更新时间平铺逻辑会话，首屏固定读取 25 条。数据本身没有丢失，但数百条会话需要逐页加载，既容易让人误以为只登记了 25 条，也不符合 DSH/Codex 以工作区组织任务的使用习惯。

## 改动

- Engine 增加统一的工作区目录读模型。底层逻辑会话、版本和平台绑定仍逐条保存；目录仅作为可重建索引，不改变同步身份。
- DSH Adapter 读取官方 `workspace.json` 中的工作区路径、标题和成员关系；Codex Adapter 读取线程 `cwd`。目录索引用规范化路径生成跨平台稳定身份，但不会替换平台会话内部的 workspace identity，也不会改变会话匹配置信度。
- 同一路径的 DSH/Codex 会话合并显示在同一个目录，来源由徽标区分；不同路径但同名的项目仍保持为独立目录。无法识别工作区的会话进入“未归类”。
- SQLite schema 升级到 v6，新增 `binding_workspaces` 索引表。升级不重写会话正文；下一次只读扫描会回填已有绑定。
- 新增 `/v1/workspaces` 目录接口，并允许 `/v1/sessions` 按工作区分页。
- Dashboard 首屏只读取工作区名称、会话数量和异常数量。展开某个目录时才读取其中前 25 条会话，可继续按目录加载；同时提供工作区名称搜索。
- Engine 版本升级到 `0.1.3`。

## 性能边界

- 不在 Dashboard 启动时加载数百条会话正文或版本图。
- 每个展开目录独立分页；刷新会清理已展开目录的临时页面缓存。
- 工作区目录逻辑集中在 Engine/Repository，CLI、API 和 GUI 共用同一归类规则，页面不自行猜测平台路径。

## 验证

- `pnpm typecheck`
- `pnpm build`
- `pnpm exec vitest run --maxWorkers=1 --testTimeout=30000`
- 结果：68 个测试文件、146 项测试全部通过。

## 回退

代码回退到本提交的前一节点后，旧 Engine 会拒绝打开 schema v6 数据库。需要同时恢复升级前的 `metadata.sqlite` 备份，或继续使用 Engine 0.1.3 及以后版本。平台原始会话与对象存储不受本次目录索引迁移影响。
