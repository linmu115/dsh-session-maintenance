## 问题与最终行为

原来 Projection Lifecycle 的 `materialize.ts` 同时负责投影目录与 SQLite canonical 数据读取；Registry 直接依赖具体 SQLite repository；Engine 分别列出三组清单/worker，又在两个回调中重复选择 adapter 实现。

现在 `CanonicalProjectionSource` 和 `IncrementalCanonicalProjectionSource` 由 contracts 定义，继续使用已有 `ProjectionRun`、`CanonicalProjectionInput`、`CanonicalChangeQuery/Page`。SQLite source 与其 SQL row 类型迁入 Store 的 `canonical-projection-source.ts`；原四个方法、SQL、排序、对象正文读取、事件索引回退与游标语义保持不变。Projection 保留读取接口的类型重导出，具体 SQLite 类只从 Store 导出。Store 不依赖 Projection 或 Adapter SDK，Projection 运行源码不再导入 SQLite。

Registry 持久化改用 contracts 的两方法 `AdapterRegistryRepository` port；Store 实现这个 port。注册 DTO、持久化记录及选择结果统一归属 contracts，其中持久化记录明确命名 `AdapterRegistrationRecord`，避免与含 source 信息的 `AdapterRegistration` 混淆。HTTP 选择结果复用同一 `AdapterSelectionReason`，没有新增并行版本 schema。Adapter Host 的 Store 依赖降为测试用 devDependency。

组装入口用一份 built-in list 配对 Alpha2、RC1、RC2 的 in-process adapter 与 worker 位置。一次 Registry 注册同时提交注册信息和可选 runtime binding；两个组装回调都从 Registry 解析运行实现。绑定 manifest 使用既有 schema 解析后完整比较；错配注册不替换旧实现。禁用注册、缺失实现均不能解析为可运行 adapter；重注册时省略 binding 会清除旧代码引用。持久化失败不会把内存注册或 runtime binding 提前发布。注册 API/选择结果只返回 DTO，不泄露函数绑定。

实际探测仍通过 `NodeAdapterWorkerFactory` 启动 RPC worker；投影操作仍使用 in-process adapter。探测支持策略未改：RC1 要求精确 package set；Alpha2/RC2 原有 compatible/experimental 诊断仍存在。Provider 精确支持矩阵未改。Runtime Broker 仍只支持原 Alpha2/RC1 event/flush 桥接，RC2 在该协议入口继续明确拒绝。
