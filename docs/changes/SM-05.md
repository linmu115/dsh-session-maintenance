## 作业与导入行为

`CodexImportService` 是 Engine 的注册实例导入入口。`content` 复用原有 Codex adapter 观察、拓扑转换和 canonical commit；`titles` 复用目录标题观察及 SM-02 元数据 helper，不读取 rollout 正文、不推进正文观察游标。投影准备前的标题观察也通过同一持久作业入口完成。

目录枚举和正文观察在全局写队列外执行，枚举及每个会话边界检查取消。正文读取前记录 canonical head；提交进入写作用域后先复验精确平台身份与 head，发生并发变化时失败为可恢复作业，恢复后重新观察。每个会话的 workspace、evidence object、canonical body/version/head、观察游标和 assignment 在同一作用域内提交，随后让出队列。原有 canonical no-op 判断保证重复观察不创建重复版本。

`operationId` 决定持久 job ID；相同 ID 和相同输入复用作业，不同输入返回 409。失败或取消后显式 resume 保留 job ID，追加事件并重新枚举；已完成会话通过 canonical 内容/元数据比较成为 no-op。源不稳定及 head 改变不会报告假成功。取消先触发内存信号，因此排队中的导入能立即感知，再经写队列持久化取消意图；已进入提交的会话完整结束，下一边界停止。取消以现有 `failed` 状态和 `JOB_CANCELLED` 事件保存，不增加平行状态机。

正常停机将中断导入重新置为 `queued`；重启恢复 `queued/running` 作业，持久取消意图则恢复成取消结果。JobRunner 的异步资源与触发 HTTP 的写作用域分离，所有运行、进度和最终状态通过 `runWrite` 持久化。同步 enqueue/resume 与启动恢复由 API 的写作用域保护。服务关闭先结束 SSE，排空作业及写队列，再删除连接描述；避免存活事件流阻止停机或在关闭后继续写响应。

## 共享合同与入口

contracts 导出 `CodexImportRequest`、`JobSummary` 和请求/列表 schema：

| 入口 | 输入 | 输出 |
| --- | --- | --- |
| `POST /v1/jobs/codex-import` | `{operationId, instanceIds, mode: 'content' \| 'titles'}` | `202 {job: JobRef}` |
| `POST /v1/jobs/:id/cancel` | `{}` | `202 {job: JobRef}` |
| `POST /v1/jobs/:id/resume` | `{}` | `202 {job: JobRef}` |
| `GET /v1/jobs/:id` | job ID | 现有 `{job, result?}` |
| `GET /v1/jobs/:id/events` | 可选现有事件游标 | 现有 `JobEvent` SSE |
| `GET /v1/jobs?kind=codex-import&limit=20` | limit 默认 20，范围 1–100，拒绝未知/重复 query | `readonly JobSummary[]`，按更新时间倒序 |

`JobSummary` 为 `{job, request: JobRequest, latestEvent?, result?, updatedAt}`。进度事件更新排序时间。所有接口使用现有 loopback 认证；输入只接受注册实例 ID，不接受来源目录。Client 增加 `importCodex`、`cancelCodexImport`、`resumeCodexImport`、`listCodexImports(signal?)`，不包含 UI 修改。

CLI `canonical import --instance <id> [--mode content|titles] [--operation-id <id>]` 默认只读取连接描述并调用在线 API。`--offline` 必须成功取得本地所有权，仍使用同一个 Engine 作业入口；在线失败没有离线降级。`sync-codex-canonical.mjs` 校验旧位置参数与已登记配置后委托此 CLI，停止直接写库。内部会话 reconcile 脚本预览改为真正只读打开；写入须显式 `--apply --offline` 并持有独占作用域。

## 全局写入协调

`MaintenanceWriteCoordinator` 由 Engine 在打开可写库或迁移前取得并持有到关闭。所有权键是 `stateRoot` 的 realpath；嵌套状态根不得绕过父根 owner，直接可写 opener 也检查所属根/祖先 owner。`maintenance-writer.json` 记录随机 owner ID、主机、PID 和 engine/offline 模式。另一进程的 owner、未知旧连接描述或未完成恢复标记均拒绝取得所有权。

写调度是应用层 FIFO，不是 SQLite transaction lock 或投影 lease。默认最多 1024 个等待/执行中的外层任务；每层子任务也有相同上限。队列满返回 `WRITER_QUEUE_FULL`，HTTP 映射 503 与 Retry-After。每个子作用域拥有独立子队列：同层 Promise.all 写入串行，后代调用可重入，因此不会形成统一 nested tail 的父子死锁。同步方法只有在无并行异步孩子时可执行，不能启动异步孩子或返回 Promise。已结束 ALS 上下文不再有写权限，延迟回调必须重新排队。

覆盖路径包括：

- Canonical/legacy Store 的 object put 至 version/head/reference 提交；元数据、墓碑、恢复、Checkpoint 与事务/continuation 写入。
- RuntimeBroker 本身的 prepare/attach/append/register/flush/drain/close/recover；由工厂提供的 ProjectionLifecycle 写入口，涵盖 WAL、receipt、投影 applied/run 状态、缓存创建及消费者生命周期。
- Adapter evidence 物理对象与登记、运行状态日志、Adapter 注册/选择、配置注册及 active DB 指针。
- 候选 reseed、RC1 preview 计划 sidecar、repair stage/activate、backup 与候选 manifest/切换。在线同进程调用复用已有 queue；独立离线调用须取得 owner。

共享接口是 `MaintenanceWriteScope.run(scope, operation, signal?)`、`runSync(scope, operation)`、`assertInScope()`、`captureEvidence()`、`assertEvidence(evidence)`。证据 shape 为 `{schemaVersion:1, ownerId, stateRoot, generation, activeScope}`；generation 在每个外层作用域进入和退出时改变，跨进程 owner ID 改变。它证明当前排他作用域，不能代替数据库/对象引用指纹，也不是嵌套 mutation 计数器。

SM-08/09 应使用注入的 `Engine.writes`：进入 `run('retention-execution', ...)` 后重新枚举并比对预览指纹，然后捕获新证据；整个最终复核、quarantine/restore/purge、恢复 journal 和实体操作都保持在作用域内，实体操作前 `assertEvidence`。预览 generation 不与执行 generation 直接比较。注册根包含关系及引用指纹由 storage governance 负责，不另建租约。

## 崩溃、陈旧锁和外部写入边界

`writer-owner inspect` 只读显示 owner；`writer-owner recover-dead --owner-id <exact-id>` 仅接受同主机且 `process.kill(pid, 0)` 已证明 PID 不存在的旧 owner。主机未知、无法查询、仍存活或 PID 被复用均拒绝，绝不凭时间过期抢占。恢复门保护核验至重命名窗口，旧 owner/匹配连接描述重命名保存为证据，再允许新进程取得 owner。若恢复动作自身崩溃留下 recovery marker，系统保守拒绝启动，须调查和人工处理该标记，不自动按年龄删除。

进程在 object put 后、数据库 commit 前崩溃，SQLite 回滚未提交引用，实体可能成为孤立对象；本项不会立即删除它，后续 retention 按完整引用清点和保留策略处理。作业提交状态与 canonical 提交可能相差一个崩溃窗口，恢复重放依靠 canonical no-op，避免重复版本。已经提交的会话不会因取消回滚。

这是协作式所有权协议，不能禁止绕过 Engine/Store 的任意第三方二进制直接改 SQLite 或实体文件；存在此类未知 writer 时不能声称可安全离线维护，必须先确认来源与独占条件。原始 Store 无 owner 的低层打开能力保留给合成测试及受控工具；生产离线入口在调用前取得 owner。所有真实 homes/state 均未写入，未运行真实清理、升级、推送或部署。
