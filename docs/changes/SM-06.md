# SM-06 — Local extraction of runtime cache responsibilities

Following the user's scope correction, this batch does not comprehensively
split ProjectionLifecycle, Runtime Broker or the plugin runtime. It extracts
the cache capability selection and close/recovery refresh operation touched by
storage governance into `packages/projection-lifecycle/src/run-cache.ts`.

The helper receives the existing run and cache attachment. It cannot create a
second run identity, change a lease, mark a run closed or remove a runtime
directory. ProjectionLifecycle still owns preparation, append/drain order,
checkpoint completion, recovery and cleanup. Both normal close and recovery
refresh the same cache, verify that its path identity has not changed, and emit
the same success/failure evidence before cleanup proceeds.

This separates cache-specific rules from the runtime state machine without
moving adapter decoding into Engine or changing projection/cache/WAL formats.
The storage service consumes durable completion evidence; directory age alone
cannot close a run or resolve a quarantine.

Validation: projection-lifecycle typecheck and 30 tests across its eight test
files, Runtime Broker and RC1 empty-session integration passed. Coverage includes
open/attach, append, persistent cache delta reuse, normal close, repeated close,
recovery with pending WAL, sparse overlay refresh, long operation IDs and the
official zero-event RC1 persisted header. Existing behavior remains the baseline.

No schema or version identity change; further extraction should follow actual
changes to synchronization/recovery responsibilities rather than file length.
