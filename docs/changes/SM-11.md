# SM-11 — Incremental latest-event index

Pure appends now verify that the existing latest-head event index is an exact
prefix of the new owned events, then insert only the suffix. Verification
compares event identity, sequence, kind, content digest and complete canonical
JSON, so source/topology corrections cannot be missed when a content digest is
unchanged. Foreign inherited events retain their original owner and are not
inserted into a derived child's mutable index.

Shorter, reordered or renormalized histories rebuild the index inside the same
version/head transaction. Retried existing version records also reconcile the
index. Historical bodies, version IDs, metadata snapshots and parent edges are
unchanged. No storage format migration or history pruning is involved.

Validation: nine focused Store tests passed, covering long appends/noop retry,
topology-only change, shortening/reordering, failed suffix and full-rebuild
insertion with atomic rollback/retry, duplicate rejection, metadata snapshots
and foreign-prefix derivation. The 19 existing canonical-engine tests also
passed in the first run; two new fixture errors were corrected (a topology
fixture missing required fields and an expected error message). Subsequent
Store checks used the repository's 15-second fixture timeout.

## Reproducible measurement

Run the Store dependency build, then
`node scripts/benchmark-canonical-event-index.mjs`. Both modes use the same
Engine commit path, body validation and compression. The comparison forces the
previous full index replacement strategy; identical SQLite triggers count
actual inserted/deleted rows. One warmup append precedes 12 measured appends of
one event each. Latencies include the counting instrumentation. Synthetic
temporary databases carry a marker and are removed after durable reopen/read.

Captured on 2026-09-06, Windows 10.0.26200, Node 24.7.0, i9-13900HX, 32 logical
CPUs. Other construction agents were active; this is a reproducible local
measurement, not an isolated hardware performance guarantee.

| Initial events | Strategy | Inserts / deletes over 12 appends | Commit P50 / P95 (ms) | New compressed body bytes |
| --- | --- | --- | --- | --- |
| 1,000 | Full rebuild | 12,090 / 12,078 | 92.11 / 134.88 | 1,069,111 |
| 1,000 | Incremental index | 12 / 0 | 73.55 / 107.76 | 1,069,111 |
| 5,000 | Full rebuild | 60,090 / 60,078 | 1,093.93 / 1,223.73 | 5,430,610 |
| 5,000 | Incremental index | 12 / 0 | 471.26 / 1,069.24 | 5,430,610 |

Raw results, event-loop delay P50/P95/max and durable reopen/read timing are in
`docs/validation/2026-09-06-sm11-index-benchmark.json`. Reopen/read is not a full
Launcher recovery benchmark. Existing close/recovery regression tests cover the
runtime path separately.

The exact write-count reduction is the strongest result. Full body reads,
serialization, hashing and compression still scale with conversation length;
body storage consumption is unchanged in this measurement. SM-12 chunking is
outside this user's selected batch.
