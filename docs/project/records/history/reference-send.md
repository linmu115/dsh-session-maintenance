用户先反馈 unknown snapshot。只读定位到 Obsidian 刷新已经持久保存新快照，而 DSH 因后续发送失败仍携带旧 hash。旧代码把可重试请求判为陌生快照，导致永久阻塞。修复为每次根据当前锚点和选中文本重新验证；旧 hash 可取回已验证的新快照，真实选区改变仍阻止发送。46 项相关测试和类型检查通过。仅替换本机刷新方法，用户重载插件后错误转为预算不足，说明已越过此关。

用户确认 CPA 与普通模型均显示额度 0。Core 原先在压缩前按完整历史字节硬扣额度，还将重放元数据计入模型文本。改为使用已注册的宿主上下文管理器先选择、必要时压缩已有历史，再以选中上下文计算；原生检查点使用匹配格式和 scope 的计数能力，普通路径只计角色与内容。没有上下文管理器的宿主保留原检查。上下文或模型在异步准备期间变化仍拒绝提交。Core 244 项测试、类型检查通过。

用户明确纠正：本次引用必须在压缩后注入，不能一起压缩。预检传入待发送消息以标识保护边界，压缩输入只从持久历史生成，本次草稿不进入压缩请求；实际发送前第二次选择以当前用户输入为保留边界，连同其后注入的引用原文一起保留，即使 retainGroups 为 1 也不能拆开。放不下时仍报错保留草稿。GPT 71 项测试通过，1 项真实网络测试跳过；专门测试确认压缩请求不包含本次输入和引用原文。

同名会话由 23:09:40 的 model/selection 事件触发派生，之后只有模型与推理设置变更，尚无新用户消息。Maintenance 把模型选择加入准备阶段事件：运行时暂缓提交，正常关闭及故障恢复也不因设置单独派生；首条真实消息到来时携带这些设置一起提交。已有派生记录未删除，避免未经确认处置会话。36 项相关测试通过。

部署使用版本化产物与 Git，不创建备份目录。期间发现 Maintenance 插件兼容名单漏加新版本，正式 repair 尝试安装旧配套包；已停止该安装，核对三个目标包和宿主构件未被替换，补齐名单后 repair connected、无 issues。使用正常关闭流程保存旧运行，更新引擎、独立 worker、插件、构件回执和实例绑定。Launcher 23:41:57 就绪，认证页面 HTTP 200，新运行 running。尚未代用户提交真实正文，因此不能宣称引用发送已成功。


23:43 的真实重试暴露两处遗漏：按钮长时间置灰后恢复，草稿仍在输入框，用户只看到闪过的报错。后台完成两段原生压缩，但没有检查点提交或新用户消息。此前只按最近历史用户消息保护，误把上一轮已完成的全部工具输出也排除在压缩外。现通过请求中的待发送消息 ID 识别边界；预检草稿未进入持久历史时，旧轮次可压缩，当前正文与引用仍原样保留。新增回归测试覆盖超长上一轮与未提交草稿；Core 244 项、GPT 71 项通过（1 项网络测试跳过），均通过类型检查。

另一次同名派生由 context/operation 而非模型切换触发。Maintenance 将 context/operation、context/operation-result、context/checkpoint、context/checkpoint-commit 同样列入准备事件，运行时与恢复判断保持一致；首条真实消息出现后再一起提交。两份相关测试共 26 项通过，插件和引擎类型检查通过。新版本已更新主引擎、独立 worker、插件、绑定回执与配套安装包；已有派生会话保留。服务启动和测试通过不代表用户正文已发送。
